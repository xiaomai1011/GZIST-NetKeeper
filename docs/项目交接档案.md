## 一、这个项目是什么

广州理工学院校园网（城市热点 Dr.COM / eportal）的**自动登录与保活工具**。Go + mygo 框架（WebView2 渲染 UI，Go 做后端），常驻托盘，掉线自动重登，支持开机自启。

- 仓库：`https://github.com/xiaomai1011/GZIST-NetKeeper`
- 本地唯一目录：`D:\Downloads\GZIST-NetKeeper\`（**既是 git 工作区，也是运行目录**）
- 作者/署名：zzstar101（GitHub `xiaomai1011`）
- 上游血缘：`YT-O5/GZIST_CampusNet_AutoLogin`（MIT），旧接口已失效，本项目重写适配 `eportal/?c=ACSetting`

**为什么要自己做**：学校的认证客户端难用、经常掉线；掉线后要手动开浏览器登录。此项目的目标是"开机就在线、掉线自己回来"。

## 四、它是怎么工作的（一条链路）

```
┌─ 计划任务（登录触发）
│    └─ GZIST NetKeeper.exe --mygo-opened-at-login
│         （mygo 会把这个参数从 os.Args 里剥离，所以日志里"参数"恒为空，属正常）
│
├─ app.ready()  main.go
│    ├─ 读设置（store）→ 账号 + 密码（keyring）
│    ├─ 建 keeper（状态机）+ 托盘 + 窗口（按需）
│    └─ go keeper.Run(ctx)          ← 单 goroutine，串行处理所有命令
│
├─ keeper.Tick（每 10s；开机 90s 内 2.5s）
│    ├─ portal.ProbeState()  →  在线 / 未认证 / 未知
│    │     ├─ 在线：HTTPS 探 baidu、qq（每个 4s，任一成功即在线）
│    │     └─ 否则取"证据"：把 http://www.baidu.com 请求出去，看是否被劫持到可信门户
│    ├─ 在线     → markOnline()，不提交
│    ├─ 未知     → 只记状态，30s 后再看，**零提交**
│    └─ 未认证   → 过了冷却才 LoginAuto()
│
└─ portal.LoginAuto（提交路径）
     ├─ 再取一次证据（与监控同一判据），只有"未认证"才继续
     ├─ 组 ACSetting 请求（账号后缀 × AC × MAC 格式），逐个试
     ├─ 门户回什么 → Classify（成功/密码错/占用/参数不匹配/未知）
     └─ 未知时等 2s 再探一次网：
          通了 → Result{Route: RouteProbe}  ← "网络已恢复，认证未确认"，**不记忆组合**
```

**两个维度永远分开**（这是整个重构的核心）：

- `NetState`：网络有没有通（在线/未认证/未知）
- `State.Auth`：上一次认证的结果（成功/未确认/失败原因）

UI 状态卡并列显示 `网络` 与 `本次认证` 两行，互不覆盖。

## 六、校园网协议知识（踩出来的）

**入口与参数**

| 用途 | 地址 |
|---|---|
| 认证提交 | `http://10.0.10.252:801/eportal/?c=ACSetting&a=Login` |
| 门户发现 | `http://10.0.10.252/`（可能 302 到别处） |
| 真实劫持页样例 | `http://10.0.10.252/a79.htm?wlanusermac=…&wlanuserip=…&wlanacip=…`（**端口 80**） |

- `DDDDD` = `,0,` + 学号（`Suffix = ",0,"`）；`upass` = 密码
- `wlanuserip` 本机 IP、`wlanusermac` 本机 MAC、`wlanacip` 接入控制器（AC）
- 旧接口 `?c=Portal&a=login` 仍保留作第二方案，但学校已基本不用

**AC 地址（重要，别乱猜）**：`10.128.255.142`、`.143`、`.129`、`.144` 都**在真实请求里出现过**。
其中 `.143` 有"发现 + 明确认证成功"记录，`.142`/`.129` 只有提交记录（抽样多返回 Portal 超时），
`.144` 出现在用户提供的真实门户地址里。**所以不能用"窄白名单"排除任何一个**，只能按"本次证据"判断。

**观察到的响应**

| 响应 | 含义 |
|---|---|
| `Dr.COMWebLoginID_3.htm` / `认证成功` | 明确成功 |
| `ldap auth error` / `密码错误` | 凭据错 |
| `已在线` / `in use` / `终端数` | 占用 |
| `AC999` | **语义未知**，按"未知服务端错误"处理（不猜、不取证） |
| `Portal协议认证超时！` | 协议层超时，常伴随链路抖动 |

**网络本身的特点（实测）**：门户（10.0.10.252）2~3 ms；外网偶发 SYN 丢弃——ping 8/8 通，但 TCP 连接会偶发 3 s / 15 s 停顿。这就是"掉线判断必须容错"的物理原因。

## 七、关键设计决策（以及为什么）

1. **三态而不是布尔**：一次 4 秒探测超时不能证明"未认证"。分成 在线 / 未认证（有门户证据）/ 未知（什么都证明不了）。**未知只复核、不提交密码**，而且复核间隔 30 s，不再是 10 s。
2. **提交前重新取证据，且与监控同一判据**：`login()` 调 `ev.state()`，不手写条件——避免"监控查了 conflict、提交忘了查"。自动路径只有 `NetUnauthenticated` 才继续。
3. **可信门户要"整体匹配"**：协议 + 主机 + 端口 + 路径作为一个组合匹配（`/a79.htm` 在 80，`/eportal/` 在 801 是提交端点，两者不能混）。参数必须齐备且等于当前网卡；有重复/冲突一律判未知。
4. **"网络通了"≠"认证成功"**：门户没确认但探测通 → `RouteProbe`，日志写"网络已恢复，认证未确认"，**不记忆参数组合**（旧代码在这里 `remember`，导致失败组合被当成最优）。
5. **只有门户明确成功才清冷却**：`markOnline` 不再清零 `Failures`；退避由真实提交结果驱动，否则抖动期会 10 秒一轮登录风暴。
6. **两个时间分开**：`NextProbe`（下次探测）与 `NextRetry`（下次允许提交）。等待冷却时复核时间对齐到冷却到期。
7. **一次点击只做一件事**：普通「登录」不解除凭据阻断、不跳冷却；未知状态变「强制登录」→ 再点「确认提交」；解除阻断用独立 `RetryCredential()`；保存账号**不触发提交**，且只有凭据**实际值变化**才解除阻断（只改学号不算）。
8. **自启用计划任务**：Run 键排在 13 个开机项的第 11 位，登录后要 75 秒才轮到它；计划任务在登录当秒触发（实测 0 秒）。

## 九、已知问题 / 明确的取舍

1. **AC999 语义未知**：按未知服务端错误处理，不做真机取证。
2. **必要参数缺失（IP/MAC/AC 任一）就不自动登录**：宁可"不登"也不瞎登。
   **若某网段门户不提供 AC，程序会一直显示"未知"而不自动登录**——这是有意的保守取舍，遇到先看日志里的 `未提交认证`。
3. **探测超时仍是 4 秒**、组合上限仍是代码推导的 16~20（未实测、未改），二期候选。
4. **真实登录验证还没做**：所有验证都是离线测试 + 日志观察。
5. **`Status.Auth` 只在本次进程内**，重启后显示"—"，属预期。
